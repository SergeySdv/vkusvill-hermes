# E2E: что именно проверяется

## Дополнения: регрессии по подходу Hermes

- Обычный CI: unit + реальный HTTP/SDK/CLI, без LLM и ВкусВилла.
- Container smoke и scanner запускаются также на PR с изменениями кода/стенда.
  Установка CLI из GitHub и live doctor остаются отдельными ручными проверками.
- Добавлены HTTP 401/403/429/500/503, таймаут, пагинация и зацикленный cursor,
  отсутствующий инструмент, повреждённый ответ и изоляция профилей.
- Обрыв после приёма cart-link запроса проверяется настоящим оборванным HTTP
  ответом. Новый процесс CLI не должен повторить мутацию. MCP tool error после
  отправки тоже считается неопределённым исходом, а не разрешением повторить.
- Проверка маркера секрета охватывает stdout и stderr CLI.
- `candidate-install` и `install` повторяют setup и требуют `reused=true`.
  Это идемпотентность runtime, НЕ доказательство обновления между двумя релизами.
- Модельные сценарии `price-change` и `uncertain` проверяют сохранение бюджета
  и запрет повторной отправки. Семантика объяснения пользователю требует review.

Повторные модельные прогоны (платные, только с отдельными test credentials):

```sh
uv run --locked python -m e2e.suite --env-file /absolute/test.env --repeats 3
```

Каждый сценарий запускается в новом контейнере. Все результаты учитываются;
повтор не заменяет неудачный прогон. Credentials-файл должен иметь права 600.
Предельное время одного контейнера — 420 секунд; лимит расходов задайте у провайдера.

OAuth: см. [подтверждённый discovery и следующий checkpoint](../references/oauth-onboarding.md).
Авторизация, настоящий модельный прогон и upgrade между релизами не считаются
проверенными результатами синтетических тестов.

## Контрольные точки 2026-10-05

| Проверка | Статус | Граница результата |
|---|---|---|
| Локальные unit/протокольные тесты | PASS | Синтетический MCP, не каталог ВкусВилла |
| Протокол + graders внутри Linux/Hermes image | PASS | 30 тестов; без LLM |
| Container smoke + scanner | PASS | Кандидат, force не используется |
| Guarded candidate install + повторный setup | PASS | CLI из закреплённого release commit; reused=true |
| Live doctor текущего CLI | PASS | Только публичный MCP; auth=not_configured |
| Пять модельных сценариев | NOT RUN | Нужны явные тестовые credentials и выбранная модель |
| Установка исправления по GitHub-ссылке | NOT RUN | Кандидат не опубликован |
| Upgrade между релизами | NOT RUN | Повтор setup не заменяет проверку upgrade |
| OAuth реализация и live-приёмка | BLOCKED | Требуются параметры зарегистрированного клиента и callback |

У Linux-прогона было предупреждение pytest о недоступности cache в read-only для
пользователя каталоге исходников; тесты прошли. Для повторного запуска используйте
`pytest -p no:cacheprovider` или cache_dir внутри `/tmp`.

## Уровни

1. `make test-protocol`: настоящий CLI в отдельных процессах → официальный MCP SDK
   → локальный Streamable HTTP сервер. Без LLM, Docker и внешнего ВкусВилла.
   Входит в обычный `make test` и CI. Проверяет поиск/карточку/аналоги,
   ID≠xml_id, буквальную передачу аргументов, check/link, повтор без новой отправки,
   AUTH_REQUIRED, SCHEMA_CHANGED, изменение цены, blocking unknown и неопределённый
   результат мутации. Остальные лимиты и инварианты проверяются unit-тестами.
2. `make e2e-smoke`: реальный официальный Hermes в контейнере, обнаружение скилла
   и запуск его launcher с живым тестовым MCP, плюс сканирование исходного скилла
   и проверка разрешения установки без force. **Без LLM**.
3. Реальный Hermes + выбранная модель + тот же контролируемый сервер: пять сценариев
   `search`, `basket`, `unknown`, `price-change`, `uncertain`. Агент сам находит скилл, он не предзагружается.
   Отдельный процесс оценивает события, журнал MCP и сохранённое состояние, а не
   только текст «готово» или код выхода Hermes.
4. `make e2e-install`: чистый профиль, штатный Hermes skills install по GitHub-ссылке,
   setup.py и live doctor. Без LLM, без обхода scanner. Проверяет **опубликованную
   версию**, не локальную ветку; обращается к GitHub/PyPI и реальному публичному
   MCP только для чтения. Запускается вручную, отдельно от offline CI.

На проверенном образе scanner `skills-guard-v6` блокирует опубликованный скилл
(`3654219`): копирование полного окружения получает HIGH и приводит к CAUTION.
`subprocess.run()` даёт только информационный MEDIUM. Установщик при этом
возвращает 0, поэтому стенд дополнительно проверяет
наличие setup.py и считает отсутствие установки ошибкой. Это реальный release
blocker для установки по ссылке; `--force` стенд не использует. Preinstalled smoke
проверяет другой этап и не означает успешную установку через scanner.

В локальном кандидате окружение ограничено явным allowlist. Проверка:
`make e2e-candidate-install`. В чистом контейнере неизменённые файлы кандидата
передаются в штатные quarantine → scanner → install-policy → installation API
Hermes с уровнем community и force=False, затем запускаются setup.py и live doctor.
Этот тест использует локальные файлы вместо скачивания с GitHub и CLI из
закреплённого в скилле commit. Он не доказывает публикацию исправления;
после публикации обязателен повтор `make e2e-install` по настоящей ссылке.

## Запуск с моделью

Сначала `make e2e-build`. Создайте вне репозитория приватный файл (права 600):

```dotenv
E2E_MODEL=provider/model-name
E2E_PROVIDER=openrouter
OPENROUTER_API_KEY=your-test-only-key
```

Подставьте реальную модель и переменные своего провайдера. Используйте отдельный
ключ с лимитом расходов; 25 итераций и 240 секунд — не денежный лимит.

```sh
uv run --locked python -m e2e.docker agent --scenario search --env-file /absolute/test.env
uv run --locked python -m e2e.docker agent --scenario basket --env-file /absolute/test.env
uv run --locked python -m e2e.docker agent --scenario unknown --env-file /absolute/test.env
```

Каждый вызов создаёт новый контейнер/профиль и удаляет контейнер вместе с его
анонимным томом. Персональная `~/.hermes`, Telegram, Docker socket и рабочие
директории не монтируются. Никакие ключи хоста автоматически не наследуются.
Hermes работает непривилегированно, с local terminal **внутри** контейнера,
без gateway. Базовый образ закреплён digest; кандидат устанавливается из текущего
Docker build context с `uv.lock`. `.dockerignore` разрешает только исходники стенда.

В `.e2e-results/<run>/` остаются результат, идентификатор образа, JSONL Hermes,
журнал MCP, stderr и запрос. Каталог исключён из git. Логи могут содержать
чувствительный текст/ошибки провайдера: не публикуйте сырые артефакты. CI не
выгружает их автоматически. Не используйте производственные ключи.

## Что пока НЕ проверено этим стендом

- Это **preinstalled candidate**, не установка по GitHub-ссылке с нуля.
  Копия runtime.py получает идентификатор кандидата и локальный источник; исходный
  скилл и его production pin не меняются. Поэтому проверяется код ветки, а не
  случайно ранее выпущенная версия. Smoke не заменяет тест bootstrap/setup.py.
- Полный clean-install с агентом должен отдельно использовать публичную ссылку,
  штатный scanner Hermes и выпущенный commit. До публикации кандидата такой тест
  не доказывает его установку. Не обходите scanner через force.
- Это не проверка реальных цен/наличия. Все данные и URL фиктивны; не открывайте
  тестовую ссылку. Реальный read-only smoke выполняется отдельно через обычный
  `vv doctor --live`, без тестовых переменных. Реальные cart link — только вручную.
- Автоматический grader не оценивает все нюансы финального текста. Обязательна
  проверка предупреждений о неизвестном наличии, отсутствии оформления/оплаты
  и неподтверждённых утверждений. Запускайте сценарии несколько раз, фиксируйте
  модель/провайдера, не скрывайте неудачи повторными запусками.
- Это регрессионный стенд, не защищённая песочница для враждебного агента:
  интернет доступен для LLM, агент и fixture имеют один UID. Для adversarial
  оценок нужны раздельные пользователи/контейнеры и сетевой allowlist.
- Обновление скилла между двумя опубликованными релизами, prompt injection и
  полноценный clean-install агентом — следующие сценарии. Сетевой обрыв после
  отправки и несовместимый ответ уже воспроизводятся протокольным стендом.

## Тестовый endpoint

`VV_MCP_TEST_URL=http://127.0.0.1:<port>/mcp` работает только вместе с
`VV_TEST_MODE=1`. Разрешены только IP loopback, HTTP и точный путь `/mcp`, без
credentials/query/fragment. CLI помечает JSON предупреждением SYNTHETIC_TEST_PROVIDER.
Не используйте профиль тестового режима в production. Без override endpoint
неизменно `https://mcp.vkusvill.ru/mcp`.
